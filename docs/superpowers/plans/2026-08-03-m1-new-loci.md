# M1 New Qualitative Loci Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add two new body-part qualitative loci — `eyes` and `hide_pattern` — so the rarity histogram has more surface area for score contributions, populating the currently-thin Adapted band (score 5–8 range). Each locus follows the established 4-allele pattern: weight-0 baseline (dominant, listed first) + weight-1 dominant + weight-3 dominant + weight-3 recessive.

**Architecture:** Two new qualitative loci added to `src/sim/data/alleles.ts` (8 new alleles total) and registered in `src/sim/data/loci.ts`. No changes to the sim engine, `resolveExpressed`, `computeRarity`, or `computeStats` — the whole point of designing these systems as data-driven was that new loci drop in as pure data. Tests that used "all-baseline" or "all-neutral" constant genomes need to include the two new baselines to remain consistent, but existing test *shape* is unchanged.

**Tech Stack:** No new deps. Vite + React + TS + Vitest, existing.

**Source decisions (from brainstorm just before writing this plan):**
- 2 new loci (not 1, not 3+)
- Body-part slots, matching game-spec's "genes readable from the sprite" principle
- No `ability` field on new alleles (avoid inventing ability names; leaves room for later authored abilities)
- No `part` field on new alleles (Allele type has no `part` yet — deferred to M2)

## Global Constraints

- **Branch continuation.** Same `m1-sim-foundations` branch. Do not create a new branch.
- **TS strict.** `strict: true`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`. No `any` in `src/sim/*`.
- **`src/sim/*` PURE.** Only the existing CLI-guard exception in `src/sim/__demo__.ts`.
- **Do NOT touch:** the Allele type (no new fields), the sim engine (`genome.ts`, `rarity.ts`, `stats.ts`, `pick.ts`, `rng.ts`), any existing allele or locus.
- **Insertion order load-bearing.** Each new locus's baseline allele goes at the TOP of its locus's block in the QUALITATIVE array, so it wins same-class dominance tiebreak.
- **No abilities on new alleles.** All 8 new alleles use the `qual()` overload WITHOUT an ability parameter.
- **No `part` fields.** Deferred to M2.
- Vitest imports from `'vitest'`.
- Conventional Commits + `Co-Authored-By: Claude Opus 4.7 <noreply@anthropic.com>` on every commit.

**Design targets (informational, not asserted):**
- Adding 2 new loci with baseline-dominates draws will roughly add ~0.3–0.6 to average expressed rarity score per hatch
- Should shift some Basic mass into Variant, and some Variant mass into Adapted (currently at 2%)
- Task 3's verify:rarity output tells the truth; do NOT auto-tune thresholds based on the shift

## Self-review notes

- **Spec coverage:** eyes → Task 1. hide_pattern → Task 2. Test constants + verify measurement → Task 3.
- **Type consistency:** No new types. Two new alleles per locus with the same shape as existing qualitative alleles. `qual()` helper handles them via the existing overloads (baseline uses `drawOverride`; others use default drawWeight).
- **Placeholders:** none — every step has real code or a real command. Task 3's verify:rarity output is deliberately captured post-fact rather than pre-specified (that's the whole point of a measurement step).
- **Task splitting rationale:** Task 1 and Task 2 are symmetric; splitting them keeps each review focused on one locus and lets the reviewer catch symmetry violations (e.g., forgetting the `drawOverride 180` on the baseline). Task 3 is separate because it's cross-cutting test maintenance + measurement — a distinct concern.
- **Deliberate deviations:** none. No new fields on Allele, no abilities, no `part`. The plan matches exactly what the user chose in the brainstorming pass.
- **Distribution outcome is measured, not guaranteed.** The plan aims to shift mass into scores 5-8, but the actual outcome depends on how the new alleles' draw distribution interacts with the histogram lumping. Task 3's verify:rarity output tells the truth; if it's still off-target, that's an iteration signal for the human, not a defect in this plan.
